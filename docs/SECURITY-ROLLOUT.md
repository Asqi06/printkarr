# Security and checkout changes — 13 October 2026

These changes were prepared and checked locally before deployment. Deployment status must be verified separately from the hosting provider and live checks; no paid service or external database was provisioned during implementation.

Knowing `/admin` is not an authentication breach. Route names must be assumed public. Access depends on server-side authentication, role checks and mutation protection; changing route names would not replace those controls.

## What changed

- Production refuses demo accounts, demo sessions and plaintext staff passwords. Existing staff credentials migrate to password hashes; changing the owner password revokes staff sessions. Password checking uses asynchronous scrypt, and login/OTP requests have IP and account limits. Production OTP delivery fails closed instead of exposing codes. Guest OTP verification consumes the code against fresh state so it cannot overwrite its own consumption.
- Browser mutations require a trusted site origin. Production trusts the configured public site rather than an attacker-supplied Host header. Session cookies are HttpOnly, SameSite and Secure in production. Private pages and APIs use no-store caching. Internal diagnostics require admin authentication; public readiness returns minimal status. Agent health requires its bearer token. Logs omit query strings and shared-file tokens.
- CSP uses a new nonce for each response, permits only required third-party hosts and blocks inline event attributes, arbitrary scripts, objects and framing. AJAX print screens carry trusted scripts forward using the document nonce. Express async errors are caught and customer-facing internal errors are sanitized.
- New orders accept wallet or Razorpay. COD selection, collection and fulfilment branches are removed; the former payment endpoint returns 410. Historical records are preserved. Old unpaid COD can be cancelled without issuing wallet credit; already-paid historical cash records require manual review.
- Razorpay confirmation checks HMAC, exact provider order, payment ID, amount in paise, INR and captured status against the provider. IDs cannot be reused across checkouts. Gateway orders are saved before returning a payment link, and duplicate opens reuse the saved order. Wallet debits and confirmed purchases are idempotent. A signed `payment.captured` webhook can settle a payment after the customer closes the browser. Provider-bound checkout amounts cannot change underneath a payment. Online refunds require an actual provider refund rather than a local paid-to-refunded toggle.
- Unbound stationery reservations expire after 30 minutes and stock is rechecked before payment. Gateway-bound and in-flight reservations remain until payment reconciliation, because releasing inventory for a potentially captured payment can oversell. This deliberately favors payment safety; operations must review abandoned provider-bound reservations.
- Timestamp-generated customer/order/subscription IDs use UUIDs. Wallet top-up provider receipts stay within the provider's 40-character limit.
- Uploads are bounded to 20 MB and two concurrent parses per process; busy uploads receive a retry response. PNG geometry, decoded expansion and animated frames are validated. Existing PDF/image checks remain. Requests have bounded provider timeouts and the server drains and flushes storage on shutdown.

## Storage and concurrency

`lib/db.js` caches unchanged snapshots, gives callers independent copies and rejects stale writes rather than losing another customer's update. No-op saves avoid disk and Atlas writes. `lib/atlas.js` coalesces unsent snapshots and shares overlapping refreshes. Upload bytes are synchronized before publishing their records; cleanup runs after durable state publication and protects active files. A stale Atlas instance refuses to overwrite newer state.

The present persistence model is still one JSON state document with a 12 MB application safety limit. Run **one web process/instance**. Redis rate limits do not make wallet or inventory writes safe across multiple workers. Before horizontal scaling or approaching the document ceiling, move orders, wallets, stock and sessions to indexed collections with transactional/atomic financial writes, then load-test that deployment. Upload restoration at boot also needs object-storage/on-demand delivery before the free storage ceiling is approached.

This is a strengthened existing application with clearer shared security/payment modules, not a claim that a complete architecture rewrite or every possible vulnerability has been addressed.

## Validation

- All 88 unit checks pass. They cover authentication, trusted origins, payment capture/binding/replay, Redis failures, cookie parsing, uploads, wallet and stale database writes.
- Checkout, store, delivery, print-option UX, Atlas safety, print safety and SEO checks pass locally.
- The isolated production-mode load check runs 100 concurrent reads, 100 distinct wallet payments and 100 duplicate requests for one checkout. It verifies exactly one debit per checkout and no cross-account mutation. It also exercises admin isolation, private diagnostics, OTP consumption/replay, COD rejection and production cookie/CSP behavior.
- Headless Edge checks the upload/options/wallet flow under production CSP at 320, 390 and 1440 px. The broader page coverage check rendered 99 pages/states and checked additional tablet sizes.
- The dependency audit returned zero known vulnerabilities at the time of this change. This does not cover unknown vulnerabilities or external service configuration.

The latest 100-user run completed concurrent reads in 3.18 seconds and distinct wallet payments in 3.86 seconds (wallet request P95: 3.57 seconds), with 100 correct debits and one debit for the duplicate-retry checkout. The test uses local synthetic data. It is not a live Atlas/Razorpay benchmark or a guarantee for 100 simultaneous large uploads. Live Atlas persistence, real captured payments/webhook delivery, hosted Redis, the Docker image and GitHub Actions must be smoke-tested in staging before production activation. No customer payment was taken by these checks.

Runnable checks: `npm test`, `npm run test:checkout`, `npm run test:store`, `npm run test:delivery`, `npm run test:ux`, `npm run test:security`, `npm run test:atlas-safety`, `npm run test:print-safety`, `npm run test:seo`. Browser variant: `node scripts/security-load-check.mjs --browser` with an installed Playwright module (or its absolute path in `PRINTKARR_BROWSER_MODULE`).

## Production activation

1. Back up durable database state and uploads. Use one instance, `NODE_ENV=production`, the correct HTTPS `PUBLIC_SITE_URL`, a unique owner password of 12–200 characters and working email delivery. Set `TRUST_PROXY_HOPS` to the actual trusted reverse-proxy chain; do not expose the application around that proxy. Check existing staff credentials and expect sessions to expire after password migration/rotation.
2. Supply production Razorpay keys. Configure `RAZORPAY_WEBHOOK_SECRET` and register `https://YOUR-DOMAIN/api/payments/webhook` for `payment.captured` using the same secret. Test a real small payment, callback replay, browser-close settlement and a wallet top-up. Registering the webhook is an external dashboard step; code alone does not enable delivery. Follow [Razorpay integration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/) and [webhook validation](https://razorpay.com/docs/webhooks/validate-test/).
3. Optional shared rate limits: provide `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` for a permanent HTTPS database. With both unset, built-in in-memory limits work for the single instance. Redis requests use an atomic EVAL operation and fail closed on service failure. The token stays server-side. No new dependency is needed. The [Upstash free plan](https://upstash.com/pricing/redis) has finite storage/command allowances; check the current allowance and projected traffic before enabling it. Each HTTP call may account for multiple Redis commands, so measure actual usage. Redis here is for rate limiting, not a cache of financial truth.
4. GitHub CI installs locked dependencies, audits and runs regression/load checks on pushes and pull requests. Actions are pinned to verified commit hashes with read-only repository permissions. The optional deploy job runs only after checks pass on `main` and only when the repository secret `RENDER_DEPLOY_HOOK` exists. Disable any independent automatic deployment that would bypass that gate. A deploy hook triggers a deployment; it does not verify that deployment's health. GitHub's [included Actions allowance](https://docs.github.com/en/billing/reference/product-usage-included) depends on repository visibility and plan.
5. The Docker container runs as user `node` (UID 1000). For an existing bind-mounted data directory, back it up and grant UID 1000 access as described in `deploy/README.md`; source code remains root-owned. No production host ownership was changed locally.
6. After deploying to staging, check `/api/ready`, authenticated `/api/ready/details`, customer login, upload, wallet checkout, real Razorpay callback and signed webhook, partner fulfilment and agent heartbeat. Check logs and persistence after a restart. Then promote the tested release with a rollback backup available.

Free hosting is not an always-on scaling promise. [Render Free](https://render.com/docs/free) spins idle services down; [free web services cannot horizontally scale](https://render.com/docs/scaling). Redis/CI can use free allowances, but hosting, backups, provider fees and sustained storage/traffic have separate limits. Nothing billable was activated during this work.
